# SecurityProfile 策略下发方式基准评估

测试日期：2026-11-07。所有方案均为隔离的基准原型，未修改生产下发链路或部署，远端集群未变更。

## 结论

- 把 SNI/TCP 放进一个 message 后继续内嵌，性能和现有分别内嵌接近；主要收益是统一消费结构。
- 独立的统一 SP 引用，在共享度高时，显著减少重复传输、编译和内存。每个 Workload 都使用独立策略时，这些收益基本消失。
- 请求时读取共享策略，增加少量缓存查找与 Arc 克隆；预先绑定可以减少这部分工作，但引入反向依赖，并把共享更新变成按 Workload 扇出的重新绑定。本组包含 SNI 元数据生成的热路径中，没有测到预先绑定的稳定整体优势。
- SNI/TCP 分别作为独立资源引用，性能收益不足以抵消版本配对、缺失和更新顺序的复杂度。两者分别内嵌于同一 WDS 更新时，没有这个资源内部的版本窗口。
- 仅拆成不同 `.proto` 文件、保持相同 message 和字段，不改变 protobuf 线格式，不构成独立性能方案。

## 原型范围与验收

基准使用现有 Workload、PolicyReference、DeltaDiscoveryResponse protobuf、生产 `tcp::Policy::compile/matches` 和 `view::project_rules`。新统一 SP 只是测试文件内的 prost message；没有新增生产 xDS 类型、订阅或 API。

所有 Workload 含 20 个标签，并保留现有供 EPE 使用的有序 SP 引用。三种内嵌方案均在更新时编译，引用方案按独立资源编译一次并共享。测量时，统一 message 使用外层 status，分别内嵌方案使用 TCPPolicy.ready；这些字段现已从实现和基准代码中移除，下面保留当时的测量数值。策略均为控制面已经转换好的 protobuf，不包含 HTTP JSON。

自检验证：七种方案在有效输入上的 TCP 判定、SNI ext_proc 响应字节一致；同时对照生产 `view::decode`；支持首条命中、无命中后续 SP、最终默认放行；引用缺失及删除不可用、资源补齐恢复、无效 CIDR 拒绝更新并保留旧结果、旧请求快照保留完整旧配置。分别引用的测试刻意验证 SNI 更新先到时，可以观察到新 SNI 与旧 TCP 的组合。原版本另验证无效状态与合法空策略的区别；当前自检改为验证缺失策略与合法空策略的区别。

这些自检验证原型语义，不能替代未来生产实现的 ADS 集成验收。

## 比较方案

| 编号 | 方案 | 策略正文与请求行为 |
|---|---|---|
| A | 分别内嵌 | 当前方式：WDS 内分别携带合并后的 SNI、TCP 正文 |
| B | 统一内嵌 | WDS 内携带一个统一策略正文，控制面已合并适用 SP |
| C | 逐 SP 内嵌 | WDS 内携带多个完整 SP，保留 SP 边界 |
| D | 统一引用／请求时查找 | WDS 仅携带引用；共享一个 SP 资源，请求时从缓存读取有序策略 |
| E | 统一引用／预先绑定 | 独立 SP 资源；安装时绑定共享 Arc，更新时通过反向依赖重建 Workload 绑定 |
| F | 分别引用／请求时查找 | 独立 SNI、TCP 资源，请求时读取两类缓存 |
| G | 分别引用／预先绑定 | 独立 SNI、TCP 资源；任一资源更新都重新绑定关联 Workload |

Sandbox 自有策略在上述设计里都可继续内嵌。本次规模矩阵聚焦有共享收益的 Workload，未把这些原型接入 Sandbox 身份与宿主绑定链路。

## 方法

Apple M4，10 核（4 性能核、6 能效核），16 GiB，macOS 27.0.1，Rust 1.97.1，release + thin LTO，System allocator。每种场景假定同一台 Porter 已关注全部 Workload。

每个场景、方案执行 5 个独立进程，交替方案顺序、轮换场景顺序。热路径每阶段预热后测量至少 100 ms，表中为 5 轮平均操作耗时的中位数，不是请求 P50。并发测试比较 1、8 个线程；更新期间额外使用 4 个读线程，记录各轮请求延迟与更新耗时。

初始化先送达 Workload，再送达引用的策略，统一资源到达顺序。每条 Delta 响应最多 32 个资源。apply 包含 protobuf 解码、规则编译、缓存发布及旧对象释放；publish 单独记录锁内发布耗时。wire 为未压缩 Delta protobuf 字节，不含 TLS、HTTP/2 和 ACK。encode 另外记录，但包含测试数据构造，不能当作真实 Go 控制面编译耗时。

内存每个场景、方案使用 3 个独立进程，报告 `/usr/bin/time -l` 峰值 RSS 的中位数，并保留释放输入后的进程 RSS。峰值包括原型一次性构造的序列化库存、临时对象和编译缓存；释放后的 RSS 仍受分配器保留影响，均不是纯缓存 live heap。原型身份缓存使用去掉 extensions 的 Workload，生产 WorkloadView 更精简；生产 ADS 流式接收的实际峰值也可能更低，不能直接用这里的 RSS 作为容量预算。

## 热路径瓶颈

TCP 尾部命中会扫描全部适用 TCP 规则；完整路径还生成全部 SNI 动态元数据并编码 ext_proc 响应。以下不包含证书解析、生产 Discovery 租约/别名/TTL、完整身份校验、gRPC 调度或 Envoy 转发。

| 场景 | TCP 首条 µs：B / D | TCP 尾部 µs：B / D | 含 SNI 元数据 µs：B / D |
|---|---|---|---|
| 1000 W，共享 1 SP，128 TCP / 16 SNI | 0.020 / 0.046 | 0.287 / 0.312 | 14.37 / 14.42 |
| 10000 W，共享 1 SP，16 TCP / 8 SNI | 0.021 / 0.052 | 0.048 / 0.083 | 7.71 / 7.47 |
| 1000 W，共享 8 SP，每 SP 16 TCP / 8 SNI | 0.020 / 0.175 | 0.278 / 0.459 | 55.36 / 54.89 |
| 1000 W，各自 1 SP，128 TCP / 16 SNI | 0.021 / 0.049 | 0.284 / 0.313 | 14.75 / 14.53 |

引用查找会增加极短 TCP 路径的相对耗时，但绝对值较小；在包含 SNI 元数据的路径里，这部分成本被元数据构造和编码明显稀释。增加 SNI 条数会同时影响所有方案，不能靠换成引用解决。

## 压力如何随规模增长

设 W 是一台 Porter 缓存的 Workload 数，P 是每个 Workload 的 SP 数，R 是每份策略的规则规模，U 是实际唯一 SP 数，F 是一次共享更新影响的 Workload 数：

- 内嵌：策略缓存与初始正文大致随 W × P × R 增长；共享更新传输与编译随 F 增长。
- 统一引用：规则存储与编译大致随 U × R 增长，绑定随 W × P 增长。
- 请求时查找：每个请求额外读取 P 个共享策略，仍需执行实际规则匹配并生成 SNI 元数据。
- 预先绑定：减少热路径查找，但共享更新需要刷新 F 个绑定；本原型重建每个绑定时解析 P 个引用。
- 分别引用：多一类资源，部分更新可只传 SNI 或 TCP；如果同时改变二者，则需要额外保证版本关系。这里测的是同时修改二者，未测单独更新某一部分的收益。

## 错误处理与维护复杂度

| 维度 | 分别/统一/逐 SP 内嵌 | 统一 SP 引用 | 独立 SNI/TCP 引用 |
|---|---|---|---|
| 配置安装边界 | 同一 Workload 更新中安装 SNI/TCP；逐 SP 模式也保持同一更新 | 单个 SP 的 SNI/TCP 一起安装；多个 SP 与绑定之间仍可能跨版本 | SNI/TCP 分别安装，可出现混合版本 |
| 首次缺失 | 有效空策略与不可用状态 | 还需区分引用为空、正文未到、已删除 | 还需区分两类正文的独立缺失 |
| 更新失败 | 拒绝整个 Workload 更新，保留旧完整视图 | 拒绝该 SP 更新，保留其旧版本；所有引用者共享结果 | 一个资源成功、另一个失败时必须定义配对行为 |
| 冷请求 | 已知 Workload 即获得策略 | WDS 与 SP 均未缓存时，按需发现存在 WDS→SP 两层依赖 | 同样有两层依赖，SNI/TCP 可以并行订阅，不能简单说成三轮 |
| 删除与回收 | 随 Workload 缓存生命周期 | 需要策略引用、租约、删除与重连失效处理 | 同样处理两类资源及其配对 |
| 预绑定附加成本 | 无 | 需要反向依赖和绑定失效处理 | 两类更新均可能刷新同一组绑定 |

仓库已经保留 `Client::dependencies` / `DependencySet::resolve`、`pin`、`capture`、代际失效、超时和失败处理。旧 TrafficPolicy 引用消费链路也可作为同仓库参考。因此统一 SP 引用有新增复杂度，但无需重写一套 ADS 生命周期框架。

实际接入仍要覆盖：控制面独立资源发布、Store/索引/可见性、xDS 类型授权与生成器；Porter ResourceKind/View、引用解析、完整请求快照、状态处理与订阅测试。预先绑定另需反向依赖及其删除/失效维护。拆成两个资源还需制定版本配对协议，不能用一个布尔 ready 消除跨资源窗口。

引用原型只按名字查找，没有实现 UID 校验、别名、完整动态订阅、租约和重连。生产实现需要保留现有身份边界，并验证同名资源重建等受支持场景。这些成本未计入原型热路径。

## 选择建议

1. 可以先统一承载结构，保持内嵌。这一步复杂度低，也能统一 status，不需要同时引入新的依赖协议。但它不会解决重复策略正文和重复编译。
2. 若同一 Porter 上大量 Workload 共享 SP、策略较大或更新频繁，优先考虑“一个独立 SP 资源 + 有序引用 + Sandbox 内联”，从请求时复用现有 Discovery 依赖缓存开始。基准支持它的加载、更新和内存收益；不能仅为避免缓存查找就先增加反向依赖。
3. 若策略几乎不共享或每台 Porter 关注的 Workload 很少，继续统一内嵌更划算。需要根据真实 W、P、U、规则数与更新频率选择，当前没有真实用户分布，不能给出通用切换阈值。
4. 不建议把 SNI/TCP 拆成两份独立下发资源。保留两个子 message 或两个源文件都可以，它们在同一个 Workload 或 SP 资源内下发即可。

## 复现与检查

```sh
cargo test --release --locked --manifest-path extensions/porter/Cargo.toml \
  --test policy_delivery_benchmark delivery_semantics_self_check

PORTER_DELIVERY_CASE=shared-1k PORTER_DELIVERY_MODE=ref_unified_lookup \
PORTER_DELIVERY_MS=100 cargo test --release --locked \
  --manifest-path extensions/porter/Cargo.toml --test policy_delivery_benchmark \
  policy_delivery_benchmark -- --ignored --nocapture --test-threads=1
```

`PORTER_DELIVERY_MEMORY=1` 仅执行初始化与 RSS 采样。场景和模式完整列表见测试文件；批量 runner、环境、全部原始日志、中位数/min/max 和测试源快照保存在本次任务的 `policy-delivery-bench` 工件目录。正式结果为规范化到达顺序后的 210 个计时进程（1890 行数据）与 126 个内存进程（252 行数据）。另保留早期不同到达顺序的 pilot，未混入正式统计。

验证：语义自检通过；Clippy（`-D warnings`）与 rustfmt 检查通过。未修改生产链路。

本次不包含真实 TLS ADS/gRPC 时延、生产 Porter 端到端吞吐、完整 Go 控制面编译与多订阅者扇出、Linux jemalloc、缓存驱逐/断线恢复、IPv6 规模或 Envoy/EPE 转发。初始化与更新的数值是 CPU/序列化/缓存组件成本，不是客户端配置收敛时延；冷请求网络轮次来自依赖关系分析，未用人工延迟模拟成实测。
